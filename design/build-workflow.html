Building CLMS

A phased plan for the mechanism library, the flag system, and the measurement layer — plus six risks in the design as specified, and what the locked decisions (task-sequence stream, rented GPUs, 0.5B cap) change about the sizing.

Read this first

Six things to be aware of

You asked what else you should know. These are in order of how much damage they do if left until later.

Risk 01 · blocks the experiment design

"Every mechanism true or false" is 2N configurations

With ~88 non-post-hoc mechanisms, independent on/off flags describe 288 runs. Even restricted to the 15 tier-1 mechanisms it's 32,768. That's not a sweep, it's a combinatorial explosion — and it's the single most common way projects like this stall.

What you actually want, and what the flag system should make easy, is a ladder: (a) controls with everything off, (b) one mechanism on at a time — N runs, this is the ablation that answers "what did each mechanism do", (c) a handful of curated stacks combining the winners, (d) a small factorial only over the top 3–4. That's roughly N + 12 runs instead of 2N.

Design implication. Keep the per-mechanism boolean exactly as you described — it's the right interface. But add a --preset that expands to a named run-set (ablation, controls, stack_a), so the common case is one flag, not eighty-eight.
Risk 02 · blocks every conclusion

"All flags false" is a floor, not a baseline. You also need a ceiling.

Turning everything off gives you sequential fine-tuning — the forgetting floor. On its own it only lets you say a mechanism is "better than nothing," which is true of almost everything and ranks nothing. To say a mechanism works you need the upper bound too: joint training on all tasks at once, which every serious paper here reports (iCaRL, van de Ven, DER all do).

With both, mechanisms become comparable on one number — how much of the gap they close:

          A(mechanism) − A(sequential FT)
ρ(m) = ─────────────────────────────────────
          A(joint training) − A(sequential FT)

ρ = 0  no better than doing nothing
ρ = 1  matches training on all data at once
ρ < 0  actively harmful — this happens more than you'd think
Three controls, not one. Sequential FT (floor), joint training (ceiling), and independent per-task models (a second ceiling that isolates whether sharing helps at all). Build all three in phase 0, before any mechanism exists.
Risk 03 · silently invalidates results

Continual-learning results are extremely high variance

Single-seed CL numbers are close to meaningless — the plasticity paper ran 30 seeds, and the ordering of mechanisms routinely flips between seeds. Compounding it, task order changes results on the same mechanisms and same data.

Protocol from day one. Minimum 3 seeds per configuration, report mean ± std, and never rank two mechanisms whose intervals overlap. Fix one task order for the main sweep and re-run the top 3 on two additional orders. Budget for this at the start — it multiplies every run count on this page by 3.
Risk 04 · makes comparisons unfair

Cost has to be a measured output, not a footnote

A mechanism that "wins" by buffering 10% of the training data is not comparable to one that adds nothing. The survey is explicit that resource efficiency is part of the objective, not separate from it. Replay beats most architectural methods on raw accuracy while quietly storing data; memory layers add parameters; GPM adds per-layer SVDs.

Every run logs five cost numbers: added parameters, buffer bytes, extra FLOPs per step, wall-clock overhead per step, and peak memory delta. Then report ρ(m) alongside ρ(m) normalized by overhead. A mechanism that recovers 60% of the gap for 2% overhead beats one that recovers 70% for 3× the memory.
Risk 05 · costs a day the first time it happens

The folder name isn't importable from Python

Continual Learning Mechanism Stack (CLMS) contains spaces and parentheses, so it can never be a Python package name — import Continual Learning Mechanism Stack (CLMS) is a syntax error. Same for the repo root, Continual learning architecture.

Keep your folder names. Put an importable package inside: Continual Learning Mechanism Stack (CLMS)/clms/, with a pyproject.toml at the repo root so pip install -e . makes import clms work from anywhere. Display name stays yours; the import path stays legal.
Risk 06 · produces confidently wrong results

A broken mechanism looks exactly like a neutral one

If EWC's penalty is computed but never added to the loss, or a gradient projection silently operates on a detached copy, the run completes cleanly and reports "no effect." You will conclude the mechanism doesn't help. This is the most dangerous failure mode in the whole project because it's invisible.

Every module ships a self-test asserting it actually changed something — loss differs from baseline, gradient norm changed, buffer is non-empty, parameter delta is non-zero. The harness runs all self-tests for enabled mechanisms on step 0 and refuses to start if one is inert.
Locked

Decisions, and what they change

Stream: task sequence with clean boundaries. Compute: vast.ai on demand, capped at 0.5B for the first run, scaling once the approach is proven. Four consequences.

Consequence 01 · needs a choice

There is no 0.5B OLMo 2 checkpoint — and you don't want one

OLMo 2 ships at 1B, 7B, 13B and 32B. Nothing at 0.5B. And a task-sequence benchmark normally starts from a pretrained model — that's how TRACE works — so "0.5B OLMo 2" means pretraining one yourself first, which is several hundred GPU-hours before a single CL experiment runs.

OptionCost before phase 3Trade
SmolLM2-360M checkpoint~0 GPU-hoursUnder your cap, modern arch, fully open recipe. Not OLMo 2, but the mechanism code is identical — only on_model_build differs.
OLMo 2 1B checkpoint~0 GPU-hoursThe arch you want, real pretrained weights, published baselines. 2× your stated cap.
Custom ~0.5B OLMo 2, pretrainedseveral hundred+Exactly your spec. Expensive on rented GPUs, and it delays every result by weeks.
Superseded — see diagnostics-suite.html. Train from scratch, as originally intended, but run the ranking sweep at 20–50M rather than 0.5B. Several mechanisms only exist if present at initialization, so a pretrained checkpoint would measure grafting damage instead of the mechanism. Scaling down is the unlock: minutes per run, the whole sweep in an afternoon, and 0.5B reserved for the winning stack.
Consequence 02 · check at the phase-0 gate

TRACE's tasks may be too hard at 0.5B to show a gap

TRACE was built to challenge aligned 7B+ models — its eight datasets span domain QA, multilingual, code generation and math reasoning. At 360M–500M, several of those may sit near chance both before and after training, which collapses the floor–ceiling gap and makes every mechanism look identical. That is precisely what the phase-0 gate is designed to catch.

Have a fallback ready. If the gap is too small, drop to a simpler sequence — split versions of standard classification tasks, where the floor–ceiling separation is large and well documented. You lose LLM realism and keep the mechanism ranking, which is what phase 3 is actually for.
Consequence 03 · build it in phase 0, not later

Rented instances get interrupted

vast.ai instances can vanish mid-run. A six-hour run killed at hour five with no resume is a total loss, and across ~50 runs that will happen more than once.

Checkpoint-resume is a phase-0 requirement, not a phase-4 convenience — and it has to cover mechanism state, not just model weights. An EWC Fisher matrix, a replay buffer, GPM's SVD bases and continual backprop's utility counters all need to survive a restart, or the resumed run is silently a different experiment. Add state_dict() / load_state_dict() to the Mechanism contract.
Consequence 04 · invisible variance

Heterogeneous GPUs contaminate the comparison

Rented hardware varies run to run. Different cards mean different numerics, different default matmul precision, sometimes different kernel paths — and that difference will show up in your results as though it were a mechanism effect. You already have seed variance to fight; you don't want a second uncontrolled source on top of it.

Pin the GPU type for a whole sweep, log the card, driver and torch version in every run directory, and treat a mid-sweep hardware change as grounds for re-running the affected configs. Set deterministic matmul precision explicitly rather than accepting the per-card default.

Sizing the budget

Don't estimate — measure. Before committing to phase 3, run one complete config end to end on the instance type you intend to rent, and time it. Multiply by (mechanisms × seeds + controls) and you have a real number instead of a guess, plus the information needed to decide whether the sweep runs at 360M or smaller. That single pilot run is the cheapest de-risking available on this whole page.

The contract

How a mechanism plugs in

One base class, seven hooks, and three pieces of declared metadata that the harness uses to validate a config before spending a GPU-hour on it.

class Mechanism:
    name        = "ewc"
    surfaces    = ("L",)            which of A/L/O/S/D it touches
    conflicts   = ("frozen_backbone",)   cannot co-run — hard error
    requires    = ("task_boundaries",)   stream capabilities it needs
    order       = 50                deterministic hook ordering

    # --- the seven hooks ---
    def on_model_build(self, model, cfg):        A: swap/insert layers
    def on_batch(self, batch, step):             D: mix replay, reformat targets
    def compute_loss(self, model, batch, out, base_loss):  L: add terms
    def before_step(self, model):                O: project / mask / damp grads
    def after_step(self, model):                 O: reinit units, shrink+perturb
    def on_task_boundary(self, model, task_id):  Fisher, SVD bases, buffer resize
    def on_eval(self, model, task_id):           probes

    # --- required, see Risk 06 ---
    def self_test(self, model, batch) -> bool:   prove it changed something
    def cost_report(self) -> dict:               params, bytes, flops, ms, mem

Three validations that run before training starts

  • Conflict check. Two enabled mechanisms naming each other in conflicts is a hard error with an explanation. The obvious case: a frozen backbone (F05) forbids weight movement, plasticity maintenance (F12) mandates it — they cannot co-run, and discovering that at hour three of a run is expensive.
  • Capability check. A mechanism declaring requires = ("task_boundaries",) on a boundary-free stream is rejected. EWC, GPM, and iCaRL all need boundaries; DER, reservoir replay, and continual backprop don't. This distinction is easy to lose track of and produces meaningless numbers when violated.
  • Ordering. When two mechanisms write the same hook the result depends on sequence — GPM projecting gradients before versus after continual backprop reinitializes units gives different models. order makes it deterministic and reviewable rather than dependent on dict iteration.
The knob

Flag system

Flags are generated from the registry, so adding a mechanism means adding one file — never editing an argument parser.

# everything off — the forgetting floor
python scripts/train.py --config base.yaml --preset controls

# one mechanism, with its own hyperparameters
python scripts/train.py --config base.yaml \
    --mech.ewc.enabled true --mech.ewc.lambda 5000

# the full single-mechanism ablation, 3 seeds each
python scripts/sweep.py --preset ablation --seeds 0,1,2

# a curated stack
python scripts/train.py --config base.yaml --preset stack_replay_sparse
# configs/stack_replay_sparse.yaml
mechanisms:
  reservoir:      {enabled: true,  capacity: 5000}
  der:            {enabled: true,  alpha: 0.5, beta: 0.5}
  memory_layer:   {enabled: true,  slots: 512000, topk: 32, layer: 12}
  sparse_ft:      {enabled: true,  t: 500, ranking: tfidf}
  continual_bp:   {enabled: true,  rho: 1.0e-4, maturity: 100}
  ewc:            {enabled: false}
  gpm:            {enabled: false}
Every run writes its fully-resolved config into runs/<id>/config.yaml, including defaults you never typed. Six months from now the only reliable record of what a run actually did is the file the run itself wrote.
Measurement

The metrics layer

You flagged this as crucial and it is — it's also the part that has to exist before the mechanisms, because it's what turns a run into a result. Four groups.

GroupMetricsAnswersSource
RetentionAA, AIA, FM, BWT, FWT, IntransigenceDid it forget? Did learning new things help or hurt old ones?2302.00487
PlasticityDead-unit fraction, effective rank, mean weight magnitude, gradient normCan it still learn at all, or has it quietly frozen?2306.13812

Plus, if the stream involves an instruction-tuned model, the capability deltas from TRACE — general ability, instruction following, safety — because a mechanism can preserve task accuracy while destroying alignment, and task metrics alone won't show it.

The one number that ranks mechanisms

ρ(m)      = gap closed vs. the floor–ceiling span   see Risk 02
ρ_cost(m) = ρ(m) / (1 + overhead_fraction)

report both, always, with mean ± std over ≥3 seeds.
a mechanism only "wins" if its interval clears the next one's.

Evaluation cadence

Evaluate on every task seen so far after every task — that's the full accuracy matrix A[i][j], and every retention metric above is derived from it. Evaluating only on the current task is the most common way to accidentally measure nothing. Plasticity probes run on a fixed schedule during training, not just at boundaries, because plasticity loss is gradual and boundary-only sampling misses the shape of it.

Sequence

Phases

Each phase has an exit gate. Don't start the next one until the gate passes — most of the failure modes above are caught by these gates.

0Scaffold

Instruments before mechanisms

  • Vendor olmo2_cl/, pin the upstream version, verify it loads a released checkpoint and trains one step
  • pyproject.toml + the clms package skeleton so imports work
  • base.py, registry.py, compose.py — the contract and its three validations
  • Full metrics layer including the cost accounting
  • The three controls: sequential FT, joint training, per-task independent
  • Seed and task-order protocol; the run-directory and config-dump convention
Gate — the three controls run end to end on the chosen stream, at 3 seeds, and produce a floor and a ceiling that are clearly separated. If the gap is small, the stream is too easy and every mechanism will look identical.
1Vertical slice

One mechanism per surface, end to end

Prove the contract on five cheap mechanisms before writing eighty. One per surface, chosen for implementation speed rather than importance:

  • L — EWC (diagonal Fisher, quadratic penalty)
  • S+D — reservoir buffer + experience replay
  • O — shrink-and-perturb (two lines, proves the optimizer hook)
  • A — XdG random context gating (proves on_model_build without a large build)
  • D — replay mix ratio + LR re-warming
Gate — all five self-tests pass, flags demonstrably change the numbers, conflict and capability validation reject a deliberately bad config, and ρ is computable for each.
2Build-out

The tier-1 fifteen

DER/DER++, LwF, online EWC, SI, GPM, O-LoRA, memory layers, sparse memory finetuning, neuron-specificity masking, L2P, LoRA, continual backprop, replay mix, persistent fast-weight state, CLS consolidation. Each with its self-test and cost report.

Gate — every tier-1 module passes self-test and reports cost. No mechanism enters the sweep without both.
3Ablation

One at a time, small model, three seeds

~15 mechanisms × 3 seeds + controls ≈ 50 runs. Run this at the smallest model that still shows a clear floor–ceiling gap — 135M–360M, not 1B. The purpose is ranking, and ranking is preserved at small scale far more often than absolute numbers are.

Gate — a ranked table with confidence intervals, and an explicit list of mechanisms whose intervals overlap and therefore cannot be ordered.
4Stacks

Tier-2 build-out and curated combinations

Add the ~30 tier-2 mechanisms. Then 6–10 hand-designed stacks based on phase-3 results, plus a small factorial over the top 3–4 to catch interactions. This is where the four-level memory hierarchy gets tested as a whole.

Gate — at least one stack beats the best single mechanism by more than the seed variance.
5Scale

Promote winners to 1B

Only the top stack and its top 2–3 components. Re-run the full metric suite and check whether the small-scale ranking held — where it doesn't, that discrepancy is itself one of the more interesting results you'll get.
