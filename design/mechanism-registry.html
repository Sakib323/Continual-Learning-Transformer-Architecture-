The plug-in contract

Six surfaces

The reason some mechanisms "can't be injected into the model arch" is that they don't touch the model at all — they operate on the loss, the optimizer, the data stream, or a finished checkpoint. Classifying by surface first is what makes a uniform module library possible: every one of the ~95 methods below fits one or more of these six hooks.

AArchitectureChanges the model graph. Needs the forked model code.
LLossAdds a term to the objective. Wraps the training step.
OOptimizerModifies gradients or the update rule.
SStateExternal buffer or datastore. Never touches weights.
DDataChanges what batches contain or when. Wraps the loader.
PPost-hocOperates on finished checkpoints. No training loop.

The hook interface every module implements

class Mechanism:
    surfaces = ()          # e.g. ("L","S") — declares what it touches

    def on_model_build(self, model, cfg):      # A — surgery: swap/insert layers
    def on_batch(self, batch, step):           # D — mix replay, reformat targets
    def compute_loss(self, model, batch, out, base_loss):   # L — add terms
    def before_step(self, model):              # O — project/mask/damp gradients
    def after_step(self, model):               # O — reinit units, shrink+perturb
    def on_task_boundary(self, model, task_id):# Fisher, SVD bases, buffer resize
    def on_eval(self, model, task_id):         # probes and metrics

A run is then a list of mechanism names in a config. Composition is just running the hooks in order, which is exactly what you need for a sweep — and it also surfaces conflicts early, because two mechanisms writing the same hook is a signal to check the interaction rather than hope.

Build tiers. T1 build first — strong evidence, needed as a baseline for everything else. T2 build for the comparison sweep. T3 reference only — implement if a T1/T2 result points at it. Implementing all ~95 up front is not realistic; the tiering is how you get a broad sweep without a year of plumbing.

On "test all of them." Many of these are mutually exclusive by construction, not merely redundant — you cannot run a frozen backbone (F05) and plasticity maintenance (F12) in the same run, because one forbids weight movement and the other mandates it. A few are known to compound: replay + distillation, sparsity + plasticity maintenance, memory layer + consolidation policy. Design the sweep as a small set of coherent stacks rather than a full cross-product, and record which combinations were excluded and why — that record is itself a finding.

The model code

Where OLMo 2's architecture lives

Three places hold it, at different levels of abstraction. For injecting mechanisms, you want the second one.

1 · Single-file reference implementation — recommended

huggingface/transformers → src/transformers/models/olmo2/

Contains modeling_olmo2.py and configuration_olmo2.py. Roughly 600–800 lines holding everything you asked for: Olmo2Attention, Olmo2MLP, Olmo2RMSNorm, Olmo2RotaryEmbedding, Olmo2DecoderLayer, Olmo2Model, Olmo2ForCausalLM. It loads the released checkpoints directly, so you can start from a pretrained model or from scratch with the same code.

There's also a modular_olmo2.py in that directory expressing OLMo 2 as a diff against Llama — worth reading first, because it shows in a few dozen lines exactly what OLMo 2 changed (norm placement and QK-norm) rather than making you diff two 800-line files yourself.

2 · The real training stack

allenai/OLMo-core

AI2's current training framework and where OLMo 2 is actually trained. Model building blocks live under olmo_core/nn/ — attention, feedforward, rope, normalization — with the block and full model under olmo_core/nn/transformer/. Fork this if you want production-grade distributed training, FSDP, and the real data pipeline. Heavier to modify than the HF file.

allenai/OLMo

The original repo; olmo/model.py is a very readable near-single-file implementation. Primarily OLMo 1, with OLMo 2 work having moved to OLMo-core — useful as a reading reference, less so as your base.

3 · Weights and configs

huggingface.co/allenai — OLMo-2 model repos

The 1B checkpoint plus the 7B/13B/32B siblings, and the intermediate training checkpoints that make this backbone worth choosing. Pull the config from here even if you train from scratch, so your architecture matches something with published baselines.

How to fork it

Don't fork all of transformers — it's enormous and you'd be maintaining a fork of a fast-moving library. Instead vendor the two files into your own repo as olmo2_cl/, register them as a custom model, and load released weights with trust_remote_code=True. You own the file outright, mechanisms inject cleanly, and you can still pip install transformers normally for everything else.

# the injection points you'll be reaching for
Olmo2MLP.forward         → swap for memory layer / MoE / k-WTA (F04, F10)
Olmo2DecoderLayer        → per-layer routing: which blocks get which mechanism
Olmo2Model.forward       → prompt prepending (F05), persistent state (F10)
Olmo2Attention           → swap for gated linear attention (F10)
Olmo2ForCausalLM.forward → expose logits + hidden states for L and eval hooks
Verify the paths before cloning. These are from memory, not fetched. Repository layouts and exact model-repo names (the 1B was released later than the 7B/13B) shift between releases — confirm on GitHub and the HF hub first.
